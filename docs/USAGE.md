# 使用 WordGit

## 保存版本与查看历史

打开已保存的本地 DOCX，点击 WordGit 选项卡中的“提交版本”，或右侧窗格中的同名按钮。填写提交说明后，Word 先保存当前稿，插件再在后台计算并写入新增数据块。之后继续编辑的内容可另作下一次提交。

右侧窗格上半部分按位置列出批注和修订，显示类型、作者与页码。点击跳转，悬停查看内容；可筛选全部、批注或修订。选中修订后点击“接受”或“拒绝”，使用 Word 原生操作处理并自动定位下一条。到末尾会回到前面尚未处理的修订；全部处理完后显示完成提示。可使用 Word 的 Ctrl+Z 撤销操作。

下半部分显示当前分支、修改状态和提交图。拖动分隔条可以调整上下大小。选择旧提交后可预览或对比；按 Ctrl 选择两个提交可以比较两版。对比结果由 Word 生成。

“对比最新提交”比较当前稿与当前分支的最新提交，包括未保存的编辑。插件使用临时副本的最终内容进行比较，原稿已有的修订与批注保留。

## 本地分支与合并

1. 点击“新建分支”，选择起始版本并输入分支名。
2. 点击“切换分支”，选择目标分支。当前稿有未提交修改时，会询问是否先提交。
3. 点击“合并分支”，选择要合入当前分支的来源分支。插件寻找共同祖先，再由 Word 原生比较和合并生成独立审阅稿。
4. 在审阅稿中逐条接受或拒绝修订。
5. 完成审阅后点击“提交版本”，将确认结果写回原稿并建立两个父提交的合并记录。

审阅未确认前两个分支保持原状；分支或原文件在审阅期间发生变化时，插件会拒绝覆盖。分支删除仅允许删除已经合入当前分支的其他本地分支，当前分支不可删除。

“合并审阅稿”也可用于导师返稿：选一个历史基准与一份外部返稿，或按 Ctrl 选两个历史版本，交给 Word 生成修订稿。审阅稿保存在 sessions 目录，保留其路径可在重启后继续审阅。

## 导入老师返稿为分支

1. 在原稿中先提交自己送审后的修改，保留当前分支的最新状态。
2. 点击功能区 **导入审阅稿**，或右侧窗格 **导入返稿**。
3. 在提交树中选中实际发给老师的送审版本，再点击 **选择送审版本**。
4. 选择老师返回的已保存 DOCX，填写一个新的返稿分支名（如 `review/老师一审`）和返稿来源。
5. 默认勾选 **导入后与当前分支生成 Word 修订合并稿**；取消勾选时只归档返稿，之后可通过“合并分支”继续。
6. 在独立合并稿里阅读批注，逐条接受或拒绝修订。处理完所有修订后点击 **提交版本**，确认合并到当前分支。

返稿文件在导入时不会被 Word 重存、接受修订或改写作者信息。它按磁盘中保存的原始字节入库；未保存的编辑不在本次导入中。返稿来源用于 Git 提交作者，文档批注和修订作者沿用返稿原有信息。

老师返稿提交直接接在所选送审提交之后，当前分支与工作文件保持原状。提交说明记录送审提交号和返稿 SHA-256。确认合并后，结果提交具有当前稿和返稿两个父提交；原始返稿仍可预览、另存、恢复。取消审阅或合并生成失败时，已导入的返稿分支继续保留。

若当前稿仍有未提交修改，导入可以完成，自动合并会提示先提交；然后从原稿点击“合并分支”选择返稿分支。审阅期间任一分支或原稿发生变化时，插件拒绝覆盖并要求重新生成合并稿。原地合并继续要求原稿位于非同步的本地目录。

只有批注的返稿也可导入；批注意见需要你修改正文后提交，修订记录可直接接受或拒绝。需要同时保留你送审后改动的场景，应使用此分支流程；“合并审阅稿”入口仍用于所选基准与返稿之间的两稿审阅。

```text
送审 A ── 你继续修改 B ── 合并确认 M
    └──── 老师原始返稿 T ──────┘
```

## 取回旧版

- “预览”以只读方式打开旧版本。
- “另存旧版”将旧版本导出到新的 DOCX 路径。
- “恢复旧版”先归档当前稿，再替换原文件并建立新提交。

原地恢复、分支切换和确认合并要求原稿位于非同步的本地目录。OneDrive 等同步目录中的文档可以使用预览和另存功能。

WordGit 支持通过 GitHub 进行按版本协作，Word 负责排版、比较和修订。跨电脑预览时，字体、Word 版本、字段更新和打印设置仍可能影响分页。实时同屏共编不在本版范围内。

## 一份稿件关联一个 GitHub 仓库

### 第一位作者：关联已有历史

1. 打开原稿，先提交当前修改。
2. 在 GitHub 创建空仓库，保留分支初始化给 WordGit；给协作者授予相应访问权限。
3. 点击 **关联仓库**，填写 HTTPS 地址（如 `https://github.com/owner/paper.git`）或 SSH 地址，以及远程分支名。
4. 点击 **关联并获取**。此操作不会上传或覆盖正文。
5. 点击 **推送**，上传当前分支的已提交历史。

每份文档的远程关联保存在其本地历史仓库中。它沿用原来的提交号、父子关系、分支和存储格式；不重新初始化已有历史。更换仓库地址会先归档旧的远程跟踪版本，再切换地址；旧提交仍可在全部历史中查找。

### 其他作者：克隆为新的本地稿件

点击 **克隆稿件**，填写仓库地址、远程分支和新的本地 DOCX 文件名。插件下载分支和对象，校验并还原文档，将本地分支关联到所选远程分支。新电脑上的文件名和路径可以不同。

克隆不会覆盖现有文件或该路径已经保留的历史仓库。原地拉取与合并继续要求文档位于非同步的本地目录。源仓库必须包含 WordGit 历史；网页直接上传的普通 DOCX、普通代码仓库和空分支不能直接作为 WordGit 稿件克隆。

### 日常协作与分歧合并

1. 各自修改并 **提交版本**。
2. 点击 **获取**，查看远程分支及领先、落后数量。获取只下载历史。
3. 点击 **拉取**。只有对方新增提交时，插件校验工作文件后快进到远程版本；已有提交号不变。
4. 双方均有独立提交时，插件使用共同祖先和双方文档生成 Word 原生修订稿。正文原稿和双方提交在审阅期间保持原状。
5. 逐条阅读批注、接受或拒绝修订，完成后点击 **提交版本**，将确认稿写回原稿并建立两个父提交的合并记录。
6. 回到原稿点击 **推送**，再由其他作者获取、拉取该合并版本。

拉取不会覆盖未保存或未提交的本地修改。审阅期间本地分支、已获取的远程分支或原文件发生变化时，插件要求重新操作。推送使用普通 Git 非强制更新；对方先推送了新版本时，当前推送会被拒绝，需要先获取、合并。

提交图中的 `origin/分支名` 为已经获取的远程跟踪分支。可在分支筛选中查看其历史，也可预览和对比对应版本。同步数量以最近获取或推送为准，插件不自动轮询网络。

获取前会归档已有远程跟踪版本，并且不自动清理被服务器删除的分支；远端重写历史后，本机已经下载的旧版本仍可取回。推送只处理当前本地分支；未推送分支和仅在本机的归档继续保存在本机。本版未提供远程标签同步、远程分支删除或强制推送入口。

### 登录与连接

HTTPS 使用 Git for Windows 配置的凭据管理器，插件不保存口令或令牌。首次连接可能打开浏览器登录；也可先按 [GitHub 官方说明](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git) 配置 Git Credential Manager 或 GitHub CLI。SSH 使用预先配置的密钥和主机信任，插件不会通过终端索要口令。

GitHub 拒绝访问、网络超时或权限不足时，操作窗口会显示 Git 的错误。关联配置可保留供重试，已有本地历史和文档不删除。本版仅接受 GitHub HTTPS / SSH 地址；测试使用隔离的本地 Git 远程。GitHub 对旧整包大文件的限制仍适用，失败时不会通过改写历史自动绕过限制。

## 空间与历史压缩

新提交复用已经保存的相同数据块，新增变化的数据和版本清单；并非每次在硬盘多复制一整份 DOCX。图片被替换或 Word 重写压缩数据时，新增量仍可能较大。

每累计约 10 次新提交，插件在键鼠空闲约 20 秒时，以低优先级、单线程在后台整理 Git 存储。维护由插件自动执行，界面不提供手动优化按钮。提交号与版本内容保留，三种历史格式都支持继续读取。

历史不会全部常驻内存。0.9.6 起，新分块历史的提交、还原、预览、导出、对比与合并通过文件流和分块缓冲处理内容；分块清单与索引仍随块数增长。旧整包、旧拆包历史取回仍使用完整内存缓冲，Word 本身的加载、排版与比较也会占用内存。提交期间若检测到文档被其他程序改写会中止并提示重新提交。后台存储整理主要优化硬盘占用，运行时仍会使用 CPU 和内存；流式读写负责降低文档处理的内存峰值。备份、导出的恢复文档和 sessions 文件不在“优化仓库存储”的处理范围内。

## 版本信息与更新

WordGit 功能区的“关于与更新”组、右侧窗格底部均可查看当前版本。点击版本信息，查看作者、项目主页、发布记录与问题反馈链接。

点击“检查更新”后会在独立窗口中异步查询 GitHub 正式 Release，编辑区可以继续操作。关闭窗口会取消查询。没有可用正式版本、请求超时、网络失败或 GitHub 限流时会分别提示；查询本身不读取文档或历史仓库。发现新版本后使用“打开发布页”下载，再保存并关闭 Word 进行安装。

## 历史格式兼容

整包与新分块历史按原文件字节取回。旧拆包历史会逐一验证所有 DOCX 部件的长度、SHA-256 和整体指纹后重建文件；文档部件保持一致，但原 ZIP 容器编码和时间戳未保存，不能承诺整个 ZIP 文件逐字节一致。安装和升级不改写这些旧提交。
